Desenvolva uma aplicação web local completa e funcional para criação visual de layouts de sites e sistemas. Este projeto NÃO é uma landing page, mockup ou demonstração visual, mas uma ferramenta real de edição visual, semelhante conceitualmente a Canva/Figma/FlutterFlow, porém com identidade própria, sem copiar seus elementos visuais, interfaces ou identidade. O público principal são estudantes, especialmente alunos do Ensino Médio em contexto educacional da Etec Sales Gomes. Portanto, priorize uma interface limpa, intuitiva, moderna, calma, criativa, organizada e fácil de entender por usuários sem conhecimento avançado de programação.

A aplicação deve funcionar localmente, sem login, cadastro, autenticação, perfil, senha ou dependência obrigatória de servidor, conta externa ou serviço online. As funcionalidades principais devem funcionar offline após a instalação das dependências necessárias.

TECNOLOGIAS E ARQUITETURA

Utilize HTML, CSS e JavaScript, com React permitido e recomendado para estruturar o editor, componentes, estado e interface quando trouxer vantagem real. Node.js pode ser utilizado apenas como suporte de desenvolvimento/build quando necessário. Não utilizar Flask, MySQL ou banco de dados externo sem necessidade real.

A arquitetura deve ser modular, organizada, reutilizável e escalável, evitando um arquivo monolítico. Separe adequadamente componentes, estilos, estado do projeto, páginas, elementos, editor, templates, persistência, sistema de design guidelines, validações/avisos e geração de código.

Antes de implementar, analise toda esta especificação, defina uma arquitetura técnica coerente e descreva brevemente a estrutura planejada. Em seguida, desenvolva efetivamente a aplicação completa.

FLUXO PRINCIPAL

O fluxo obrigatório deve ser:

MENU → ESCOLHA DE TEMPLATE → ESCOLHA DA DESIGN GUIDELINE → EDITOR VISUAL → ADICIONAR/MOVER/REDIMENSIONAR/EDITAR COMPONENTES → CRIAR MÚLTIPLAS PÁGINAS → SALVAR → GERAR CÓDIGO A QUALQUER MOMENTO → VISUALIZAR/COPIAR/EXPORTAR RESULTADO.

A aplicação deve possuir três áreas principais:

1. Menu
2. Criação do Layout
3. Gerador de Código

A funcionalidade “Gerar Código” também deve estar disponível diretamente dentro do editor a qualquer momento, sem obrigar o usuário a sair da área de edição.

Templates obrigatórios:

O hover de cada template deve mostrar:

DESIGN GUIDELINES

Além da escolha do template, o usuário deve poder escolher uma Design Guideline antes de iniciar o layout.

Crie um sistema próprio de Design Guidelines baseado nos princípios e recomendações gerais de design presentes nas seguintes referências oficiais:

Apple Human Interface Guidelines:
https://developer.apple.com/design/human-interface-guidelines

Android Design:
https://developer.android.com/design?hl=pt-br

Microsoft Windows App Design Guidelines:
https://learn.microsoft.com/en-us/windows/apps/design/guidelines-overview

Não copie literalmente essas interfaces, componentes ou identidades visuais. Utilize os princípios de usabilidade, hierarquia visual, acessibilidade, consistência, espaçamento, legibilidade, feedback, navegação e interação como referência conceitual.

A primeira Design Guideline obrigatória deve ser uma identidade própria chamada:

“Dark Deco”

A Dark Deco deve combinar princípios de Design Digital, hierarquia visual e psicologia das cores com uma estética contemporânea inspirada em Art Déco reinterpretada para uma interface digital moderna.

A estética Dark Deco deve priorizar:

* Fundo escuro sofisticado
* Contrastes bem controlados
* Formas geométricas
* Linhas e divisões elegantes
* Tipografia limpa e expressiva
* Destaques metálicos/dourados utilizados com moderação
* Tons escuros e neutros como base
* Uma cor de destaque bem definida
* Espaçamento consistente
* Hierarquia visual forte
* Aparência sofisticada sem prejudicar a usabilidade
* Evitar excesso de brilho, gradientes ou elementos decorativos desnecessários

A Dark Deco não deve ser apenas um tema de cores. Ela deve funcionar como uma verdadeira Design Guideline capaz de orientar:

* Cores
* Tipografia
* Escala tipográfica
* Espaçamento
* Bordas
* Raios
* Sombras
* Botões
* Cards
* Inputs
* Links
* Hierarquia
* Contraste
* Estados de interação
* Organização visual
* Componentes
* Responsividade

A arquitetura deve permitir adicionar outras Design Guidelines futuramente sem precisar reescrever o editor.

Na tela de criação do projeto, permita ao usuário selecionar a Design Guideline desejada e aplicar suas regras ao projeto.

A guideline escolhida deve influenciar a aparência inicial dos componentes e também servir como referência para o sistema de análise de consistência visual.

O usuário deve poder visualizar uma pequena prévia da guideline antes de escolhê-la.

SISTEMA DE AVISOS E ANÁLISE DE DESIGN

A aplicação deve possuir um sistema inteligente de avisos que analise o layout criado e informe o usuário quando determinadas escolhas visuais ou estruturais não fizerem sentido.

Os avisos não devem bloquear o usuário obrigatoriamente. Eles devem funcionar como recomendações educacionais e de melhoria.

O sistema deve detectar, quando possível:

* Contraste insuficiente entre texto e fundo
* Texto pequeno demais para leitura
* Excesso de cores diferentes
* Cores que não possuem coerência entre si
* Uso excessivo de cores de destaque
* Componentes desalinhados
* Espaçamentos inconsistentes
* Elementos muito próximos das bordas
* Sobreposição problemática entre componentes
* Botões sem texto ou ação
* Links sem destino
* Botões apontando para páginas inexistentes
* Elementos fora da área útil
* Hierarquia visual confusa
* Títulos sem destaque suficiente
* Excesso de elementos em uma mesma região
* Layout potencialmente difícil de utilizar em telas menores
* Problemas básicos de responsividade
* Elementos importantes muito pequenos
* Componentes que possam prejudicar a acessibilidade
* Uso incoerente da Design Guideline escolhida

Os avisos devem possuir diferentes níveis, por exemplo:

* Informação
* Sugestão
* Atenção
* Problema

Cada aviso deve explicar de maneira simples:

“O que está acontecendo”
“Por que isso pode ser um problema”
“Como melhorar”

Sempre que possível, oferecer uma ação para corrigir o problema automaticamente.

O objetivo é também tornar o sistema uma ferramenta educacional, ensinando o estudante sobre princípios de design enquanto ele constrói o layout.

EDITOR VISUAL

A organização deve ser inspirada na experiência geral de editores visuais profissionais, utilizando a imagem fornecida pelo usuário como referência de estrutura e experiência, mas sem copiar identidade visual, layout exato, componentes proprietários ou aparência de Canva, Figma ou FlutterFlow.

* Mover

DRAG & DROP REAL

Drag & Drop é obrigatório.

O usuário deve conseguir arrastar componentes do painel lateral para o canvas.

A operação deve modificar o estado real do projeto.

O novo componente deve receber:

* ID único
* Tipo
* Posição
* Tamanho
* Página
* Estilos padrão da guideline
* Propriedades padrão
* Ordem/camada

O componente deve permanecer manipulável depois de inserido.

Não criar drag & drop apenas como animação visual.

CARD COMO CONTAINER REAL

O componente Card deve funcionar, quando viável, como um verdadeiro container.

O usuário deve conseguir colocar outros componentes dentro de um Card diretamente no projeto.

Por exemplo:

Card
→ Título
→ Parágrafo
→ Imagem
→ Botão

O Card deve possuir uma área interna identificável para receber componentes através de drag & drop.

Elementos internos devem permanecer associados ao Card no estado do projeto.

Permita:

* Adicionar elementos dentro do Card
* Mover elementos dentro do Card
* Redimensionar elementos internos
* Editar elementos internos
* Remover elementos internos
* Reorganizar elementos internos
* Alterar propriedades do Card
* Alterar espaçamento interno
* Definir alinhamento dos filhos
* Controlar layout interno usando conceitos como Flexbox ou Grid quando apropriado

A estrutura hierárquica deve ser preservada na geração do código.

Por exemplo, um Card contendo título, texto e botão deve gerar HTML semanticamente equivalente a um container contendo esses elementos, e não elementos independentes fora do Card.

BOTÕES E INTERAÇÕES REAIS

Todos os botões adicionados pelo usuário ao projeto devem ser funcionais.

Não criar botões falsos ou meramente decorativos.

O editor deve permitir configurar a ação de cada botão, incluindo pelo menos:

* Navegar para outra página do projeto
* Navegar para uma URL externa
* Rolar para uma seção/elemento quando aplicável
* Não executar ação, apenas quando explicitamente configurado como visual

Botões que apontam para páginas internas devem funcionar tanto na visualização do projeto quanto no código exportado.

Exemplo:

Botão “Continuar”
→ Página 2

Ao exportar, a navegação deve continuar funcionando.

LINKS DE NAVEGAÇÃO

Links também devem possuir destinos reais.

O usuário deve poder selecionar uma página interna como destino.

A exportação deve preservar essa navegação.

GERADOR DE CÓDIGO

O gerador deve interpretar os objetos estruturados do editor e convertê-los em:

* HTML
* CSS
* JavaScript

O usuário deve poder gerar código em qualquer estágio da criação.

O resultado deve refletir exatamente o estado atual do projeto naquele momento.

Após novas alterações:

GERAR NOVAMENTE → CÓDIGO ATUALIZADO.

Não utilizar screenshot-to-code.

O código exportado deve ser simples, legível e estudável, priorizando HTML, CSS e JavaScript puros, mesmo que React seja utilizado internamente na aplicação.

A saída obrigatória deve incluir pelo menos:

* Um arquivo .html funcional
* Um arquivo .txt ou .md contendo o código bruto

Preferencialmente permitir também exportar:

* index.html
* style.css
* script.js

quando a separação em arquivos for mais adequada.

O HTML exportado deve:

* Representar realmente o layout criado

* Possuir estilos reais

* Preservar navegação
* Preservar botões
* Preservar links
* Preservar múltiplas páginas
* Ser responsivo
* Poder ser aberto diretamente no navegador

Quando possível, gerar uma versão autocontida para facilitar o estudo e compartilhamento.

Os elementos criados no canvas devem possuir correspondência real no código.

O resultado final deve permitir que o usuário escolha um template, escolha uma Design Guideline, abra um projeto, edite visualmente, adicione componentes, arraste componentes, coloque componentes dentro de Cards, redimensione elementos, altere propriedades, crie páginas, conecte botões e links, receba recomendações de design, salve localmente, visualize o resultado, gere código em qualquer momento e exporte um site funcional e responsivo.

A ferramenta deve ser realmente utilizável por um estudante, e não apenas parecer uma ferramenta de criação visual.
